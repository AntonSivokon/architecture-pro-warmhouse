# Задание 1. Анализ и планирование

### 1. Описание функциональности монолитного приложения

**Управление отоплением:**

- Пользователи могут удалённо включать/выключать отопление в своих домах.
- Система поддерживает получение состояния всех датчиков и конкретного датчика.
- Система поддерживает регистрацию нового датчика, обновление данных о датчике и удаление датчика из системы.

**Мониторинг температуры:**

- Пользователи могут просматривать значение температуры в определенной локации.
- Система получает данные о температуре с датчиков, установленных в домах.

### 2. Анализ архитектуры монолитного приложения

- **Язык программирования**: Go
- **База данных**: PostgreSQL
- **Архитектура**: Монолитная, все компоненты системы (обработка запросов, бизнес-логика, работа с данными) находятся в рамках одного приложения.
- **Взаимодействие**: Синхронное, запросы обрабатываются последовательно.
- **Масштабируемость**: Ограничена, так как монолит сложно масштабировать по частям.
- **Развертывание**: Требует остановки всего приложения.

### 3. Определение доменов и границы контекстов

- **Домен: управление отоплением** - система работает с показаниями датчиков в доме.
  - **Поддомен: управление датчиками**. Он включает создание, просмотр, изменение и удаление датчиков, обновление их значений и статусов.
  - **Поддомен: мониторинг температуры**. Он включает получение актуальной температуры из датчика в определенной локации.

### **4. Проблемы монолитного решения**

#### Проблемы поддержки приложения:
- **Высокий риск ошибок.** В целевой экосистеме предполагается расширение функциональности приложения и пересмотр архитектуры, поэтому изменения в одной части приложения могут непредсказуемо влиять на другие части. Из-за этого возрастает вероятность возникновения ошибок.
- **Длительные циклы разработки и развёртывания.** При каждом изменении приходится тестировать всё приложение целиком. После реализации MVP вероятно предстоит разработка новых функций системы. Монолитное решение замедлит выпуск новых функций.
- **Управление командой**. Внесение изменений в монолитное приложение, может блокировать задачи, которыми занимаются разные команды.
- **Масштабирование**. В целевой системе планируется создание экосистемы умных посёлков на территории нескольких регионов страны и, как следствие, увеличение нагрузки на некоторые части приложения в связи с увеличением объема данных и количества пользователей. В монолитном решении не получится точечно масштабировать систему.

Все эти факторы замедляют внедрение новых функций, усложняют обслуживание системы и увеличивают время выхода на рынок. Это тормозит развитие бизнеса.

#### Проблемы архитектуры и бизнес функциональности:
- **Отсутствие профиля пользователей.** В данном решении непонятно какое устройство к какому пользователю относится. Это делает невозможным процессы автоматизации и усложняет решение инцидентов по конкретному устройству.
- **Отсутствие уведомлений пользователей.** Для системы отопления может быть критичным отсутствие уведомлений о неисправности или неожиданном отключении отопления. 
- **Ограниченная функциональность для пользователя.** Нет возможности гибкой настройки работы с датчиками и ограничены получаемые данные.

# Задание 4. Создание и документирование API

### 1. Тип API

Для взаимодействия микросервисов используется **гибридный подход: REST API для синхронных запросов и Kafka для асинхронного обмена событиями**.
Это соответствует разделению взаимодействий на диаграммах: API Gateway обращается к сервисам по REST/HTTP с JSON, а телеметрия, состояния устройств, команды и события уведомлений передаются через Kafka.

**REST/HTTP (JSON)** подходит для операций, где вызывающему сервису нужен немедленный результат: получение данных и управление устройствами, домами, пользователями, настройками автоматизации и уведомлений.
Такой интерфейс понятен клиентам, легко документируется в OpenAPI и позволяет явно описывать ресурсы, операции и коды ответов.

**Kafka** используется для событийного взаимодействия, не требующего немедленного ответа.
Например, Telemetry Service публикует данные в топики `iot.telemetry` и `iot.device-state`;
Device Service получает события состояния и обновляет данные устройства;
Automation Service обрабатывает телеметрию и публикует команды в `iot.device-command`, а события уведомлений передаются через `iot.notification`.
Подписчики обрабатывают сообщения независимо, что снижает связанность сервисов и помогает выдерживать всплески нагрузки и временную недоступность потребителей.

**MQTT** остаётся протоколом обмена непосредственно с IoT-устройствами и не используется как основной API между микросервисами.

### 2. Документация API

Для основных синхронных операций Device Service и Telemetry Service спроектирован REST API из пяти операций:

[OpenAPI 3.1 - Device Service и Telemetry Service](docs/api/openapi.yaml)
- список устройств пользователя;
- получение устройства с состоянием;
- регистрация устройства;
- отправка команды устройству;
- запрос получения данных телеметрии по устройству.

В асинхронном API описываются схемы сообщений и примеры для топиков `iot.telemetry`, `iot.device-state`, `iot.device-command` и `iot.notification`.

# **Задание 6. Разработка MVP**

Добавлены [Device Service](apps/device_service) на Python/FastAPI и [Telemetry Service](apps/telemetry_service) на Java с Kafka
Streams. Telemetry Service получает показания через существующий REST API Go
монолита. Снимки публикуются в Kafka и
обрабатываются в топики `iot.telemetry` и `iot.device-state`.

Для запуска MVP создан отдельный самостоятельный Compose-файл
[apps/docker-compose.mvp.yml](apps/docker-compose.mvp.yml), включающий базовые
сервисы монолитного приложения и расширяющий сервисами Device Service, Telemetry Service и Kafka.

Для проверки можно использовать [API сервисов из Задания 4.2](docs/api/openapi.yaml), API уже настроено на правильные порты localhost.

Комментарии по некоторым точкам для MVP:
- `GET /api/v1/users/{userId}/devices` - User Service не реализован в MVP, поэтому данный запрос возвращает устройства без фильтрации по userId (можно указать любой UUID). С помощью этой точки можно посмотреть все устройства и получить их ID в виде UUID, например для запроса телеметрии по устройству
- `POST /api/v1/devices` - создает устройство вызовом API монолитного приложения. По созданным устройствам Telemetry Service будет запрашивать и сохранять телеметрию (показания датчиков температуры).
- `POST /api/v1/devices/{deviceId}/commands` - в MVP не реализована интеграция с сервисом Automation Service, данный метод просто отправляет сообщение в брокер.
- `GET /api/v1/devices/{deviceId}/telemetry` - в MVP не реализована интеграция с InfluxDB. Данные телеметрии сохраняются в Kafka Store (последние 100 записей по устройству).
